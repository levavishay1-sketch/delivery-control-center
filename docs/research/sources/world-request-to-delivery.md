## 1. AI-native issue/requirement handling in 2026

### Linear
- **Linear for Agents** (May 2025): agents are first-class users — assign, @mention, scoped permissions; agents "triage issues, answer questions, create follow-up work… draft branches from assigned issues". https://linear.app/agents [A, vendor page, read via search snippet]
- **Agent Interaction SDK** (developer docs): assigning an issue to an agent sets it as **`delegate`, not `assignee` — "so humans maintain ownership while agents act on their behalf"**. Every delegation opens an *agent session* whose state "is visible to users, and updated automatically based on the agent's emitted activities" (thought / action / elicitation / response / error); the agent must "emit a `thought` activity within 10 seconds". Apps in `actor=app` mode cannot request `admin` scope. https://linear.app/developers/agents [A, read from a scraped copy]
- **Triage inbox** is Linear's "draft-first" intake: issues from integrations or from people outside the team land in Triage; the team **Accept / Decline / Mark as duplicate / Snooze** before anything enters the backlog. https://linear.app/docs/triage [A]
- **Triage Intelligence / Product Intelligence** (tech preview Aug 14 2025; auto-apply Sept 19 2025): suggests team, project, assignee, labels, related issues and duplicates; each suggestion shows its reasoning and is **accepted or declined**; per property type an admin chooses whether suggestions "appear, are hidden, or are auto-applied"; "processing new issues in Triage is expected to take 1–4 minutes". Models: GPT-5 / Gemini 2.5 Pro class. https://linear.app/docs/triage-intelligence · https://linear.app/changelog/2025-09-19-auto-apply-triage-suggestions · https://linear.app/now/how-we-built-triage-intelligence [A/C — no accuracy numbers published in the parts I could read]
- **Linear Agent writes code** (posts: "How we use Linear Agent at Linear" Apr 10 2026; "Now Linear writes the code too" Jun 11 2026; "Reviewing code in the agent era" Jun 10 2026 — "between January and March our total issues created and PRs merged both climbed by 50%"). Only the RSS excerpts were readable. https://linear.app/now/now-linear-writes-the-code-too [C]
- Where Linear insists on a human: ownership (delegate model), triage acceptance, per-property auto-apply opt-in, PR review. Where it automates: routing, labels, duplicates, first-draft branches.

### Atlassian Jira / Rovo
- **"Suggest work items"** (native Jira Cloud): "You can use AI to generate a list of suggested child work items, based on the details of the parent work item… which you can accept, edit, or decline. When you accept a suggestion, a new child work item will be created and linked to the parent." Nothing is created without acceptance. https://support.atlassian.com/jira-software-cloud/docs/create-a-work-item-and-a-subtask/ [A, read from a scraped copy]
- **Create work items with Rovo** (chat): Rovo "will generate a set of suggested work items for you to review, refine, and then add". https://support.atlassian.com/jira-software-cloud/docs/create-work-items-with-rovo/ [A, snippet]
- **Rovo Dev** (GA Oct 2025): CLI, a workflow tab inside Jira, PR review in Bitbucket/GitHub, VS Code. Atlassian's own account: "get Rovo Dev to do an initial investigation and break it down onto individual Jira work items that you (or the agents) can then work on in parallel" — "Delivering 120 PRs in two weeks with Rovo Dev in Jira". https://www.atlassian.com/blog/development/120-prs-two-weeks-rovo-dev-in-jira [C, vendor]
- Marketplace apps (e.g. Smart AI for Jira "AI Work Breakdown") add chat-to-edit before pushing subtasks. [C]

### Azure DevOps Boards + GitHub Copilot
- **Assign a work item to Copilot coding agent**: public preview Sept 18 2025 (https://github.blog/changelog/2025-09-18-assign-azure-boards-work-items-to-copilot-coding-agent-in-public-preview/), GA Dec 2025. What is sent: "title, large text fields (such as description and acceptance criteria), comments, and a link to the work item" (the changelog says the last 50 comments). Copilot "create[s] a branch and draft pull request in the selected GitHub repository" linked back, and the card shows **In Progress / Ready for Review / Error**. The human must "review… convert the draft pull request… approve… merge… update your work item state". Explicit limits: **"Copilot doesn't handle dependencies between work items. Keep each work item self-contained"**, "Overly complex or verbose work item descriptions can reduce Copilot effectiveness", "You can't cancel it." Requires GitHub-hosted code and GitHub App auth (PATs unsupported). https://learn.microsoft.com/en-us/azure/devops/boards/github/work-item-integration-github-copilot [A]
- Sprint 269 (Feb 12 2026): pick a **Copilot custom agent** when creating the PR from a work item. https://learn.microsoft.com/en-us/azure/devops/release-notes/2026/sprint-269-update [A]
- **No AI breakdown of work items exists natively in Azure Boards** (nothing in the 2025–2026 release notes I could read; only third-party extensions). Absence noted, not proven.

### GitHub Copilot coding (cloud) agent
- Assign an issue → agent "research[es] a repository, create[s] an implementation plan, and make[s] code changes on a branch"; pushes to a **draft PR**, requests review. Hard limits: "maximum execution time of 59 minutes", "can only work on one branch at a time and can open exactly one pull request"; for bigger work "consider breaking the work into smaller, more focused tasks". Workflows on its PRs "require approval from a user with write access before they will run"; the requester cannot be the approver. https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent · https://docs.github.com/en/copilot/responsible-use/agents [A]
- Task-writing guidance: an ideal task has "a clear description of the problem", "complete acceptance criteria on what a good solution looks like", "directions about which files need to be changed"; avoid "ambiguous… open-ended" and production-critical/security tasks. Iterate with `@copilot` PR comments; batch them with "Start a review". https://docs.github.com/en/copilot/tutorials/cloud-agent/get-the-best-results [A]
- **It does not ask clarifying questions**: the community request "Allow/force copilot to ask clarification questions" is unanswered; practitioners report "the agent tends to wander and produce a weak or off-target first PR" without repo instructions. https://github.com/orgs/community/discussions/169482 · https://github.com/orgs/community/discussions/170528 [C]. The **Copilot CLI plan mode** (Jan 21 2026) is the exception: an `ask_user` tool asks scope questions and the plan lists "any open questions". https://github.blog/changelog/2026-01-21-github-copilot-cli-plan-before-you-build-steer-as-you-go/ [A, snippet]
- **Draft issues** in GitHub Projects "exist only in your project" until converted (no repo, labels, milestone). https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-items-in-your-project/adding-items-to-your-project [A]
- **Issue dependencies** ("blocked by"/"blocking") with a Blocked icon on boards; `gh issue create --blocked-by`. https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies [A]
- Evidence that the ticket, not the model, dominates outcome: a study of ~3,180 Copilot-authored PRs / 2,000+ assigned issues found ticket features predict merge at 72% AUC; self-contained issues +16.65% merge rate, well-scoped +16.44%, concrete steps +7.58%, named files +6.4–7.2%; **verbose descriptions −9%**, external-dependency mentions −4–9%. https://arxiv.org/abs/2512.21426 [B, secondary quotes]

### ClickUp / Monday / Notion
- ClickUp Brain: AI actions inside automations ("when a task is created… use AI to generate a task description from the title"), agents that create/schedule tasks. Monday AI: intake/approval board templates. Notion AI: document-centric. None documents a clarification step or a human-gated breakdown comparable to Jira's "suggest work items". [C, thin coverage]

**Take-away for DCC.** Every vendor automates routing, duplicate detection and *proposed* children; every vendor keeps a human on: accepting the proposal, owning the item (Linear's delegate), approving the PR, and approving CI. Nobody has shipped an autonomous requirement-clarifier; the only shipped "ask" surfaces are plan modes (Claude Code, Cursor, Codex, Copilot CLI), i.e. inside the developer's session, not in the tracker.

## 2. Clarification-question research and what tools do before coding

### Benchmarks and studies
| Work | What it measured | Result | Grade |
|---|---|---|---|
| **ClarifyGPT** (FSE 2024) — https://arxiv.org/abs/2310.10996, code https://github.com/ClarifyGPT/ClarifyGPT | detect ambiguity by a *code-consistency check* (sample several implementations; disagreement ⇒ ambiguous), then ask targeted questions | GPT-4 pass@1 on MBPP-sanitized 70.96% → 80.80%; average over five benchmarks 62.43 → 69.60 (GPT-4), 54.32 → 62.37 (ChatGPT); 10-person user study; simulated users | B |
| **Ambig-SWE** (ICLR 2026) — https://arxiv.org/abs/2502.13069 | underspecified variants of SWE-Bench Verified with a simulated user holding the full spec; three skills: use interaction, detect ambiguity, ask targeted questions | "models struggle to distinguish between well-specified and underspecified instructions"; interaction gives "up to 74% improvement over the non-interactive settings"; secondary note: removing detail dropped Sonnet 4 ≈65% → ≈42%, detection near chance | B |
| **Ask or Assume?** (Mar 2026) — https://arxiv.org/abs/2603.26233 | a second agent dedicated to *detecting* underspecification, decoupled from the coding agent | OpenHands + Claude Sonnet 4.5: **69.40% resolve vs 61.20% single-agent**, "closing the performance gap with agents operating on fully specified instructions"; "conserving queries on simple tasks" | B |
| **CLARITI / Asking What Matters** (Apr 2026) — https://arxiv.org/abs/2604.14624 | Shapley attribution of which missing information predicts success + which questions users can actually answer | an 8B clarification module "matches GPT-5's resolution rate on underspecified issues while generating **41% fewer questions**" | B |
| **HiL-Bench** (Apr 2026) — https://arxiv.org/abs/2604.09408 | tasks with 3–5 human-validated blockers that "surface only through progressive exploration, not upfront inspection"; agents get `ask_human()`; metric **Ask-F1** = harmonic mean of question precision and blocker recall ("architecturally prevents gaming through question spam") | frontier agents ≈90% pass@3 with full information, collapsing when blockers are present (one secondary note: 75–89% → 4–24%); RL on Ask-F1 improves a 32B model | B |
| **Ask Early, Ask Late, Ask Right** (May 2026) — https://arxiv.org/abs/2605.07937 | forced-injection of ground-truth clarifications at controlled points; 6,000+ runs, 4 models | **goal clarification loses nearly all value after 10% of execution** (pass@3 0.78 → baseline); input clarification keeps value to ~50%; "deferring any clarification type past mid-trajectory degrades performance below never asking at all"; in 300 unscripted sessions "no current frontier model asks within the empirically optimal window… over-asking (52% of sessions) to never asking" | B |
| **ClarifyCodeBench** (Jul 2026) — https://arxiv.org/abs/2607.00711, code https://github.com/fangz-cs/ClarifyCodeBench | 419 LiveCodeBench tasks with annotated key questions; metrics TKQR (asks the key questions early) and **ORA** (Gaussian penalty on asking more rounds than needed) | secondary notes: models *under*-ask rather than over-ask; clarification quality degrades as the number of ambiguities grows; "strong code generation does not imply strong clarification" | B |
| **Dialogue SWE-Bench** (Jun 2026) — https://arxiv.org/abs/2606.13995 | persona-grounded user simulator; dialogue quality scored | schema-guided dialogue agent +3–14%; "better coding models do not always correspond to better dialogue models" | B |
| QuestBench (DeepMind 2025) — https://arxiv.org/abs/2503.22674 | find the single missing variable | >80% on simple algebra, sharp degradation on logic/planning — detection is domain-dependent | B, secondary |

Standing caveat (raised by the field itself, e.g. "Humans are Missing from AI Coding Agent Research", https://arxiv.org/abs/2608.12355): **every clarification study simulates the user from the gold answer; none uses real clients on real repository issues.** Effects on real stakeholders with month-long answer latency are unmeasured.

### What the tools do before coding
- **Claude Code plan mode**: "Claude reads files, runs shell commands to explore, and writes a plan, but does not edit your source"; approval options "Yes, and use auto mode / Yes, manually approve edits / No, keep planning"; `Ctrl+G` to edit the plan; official advice "If you could describe the diff in one sentence, skip the plan". Questions go through `AskUserQuestion`: **1–4 questions per call, 2–4 options each, multi-select, free-text "Other"**; not available to subagents. Auto mode "nudges Claude to keep working without stopping for clarifying questions". Recommended larger-feature flow: "Interview me in detail using the AskUserQuestion tool… Keep interviewing until we've covered everything, then write a complete spec to SPEC.md", then "start a fresh session to execute it". https://code.claude.com/docs/en/permission-modes · https://code.claude.com/docs/en/agent-sdk/user-input · https://code.claude.com/docs/en/best-practices [A]
- **Anthropic's usage data** (millions of sessions): "people make about 70% of the planning decisions but only 20% of the execution decisions"; "on the most complex tasks, Claude Code asks for clarification more than twice as often as humans interrupt it"; full auto-approve rises from ~20% (new users) to >40% (750+ sessions) while interrupt rates also rise (5% → 9% of turns); novice sessions reach verified success 15% vs 28–33% for experts. https://www.anthropic.com/research/claude-code-expertise · https://www.anthropic.com/news/measuring-agent-autonomy [B]
- **OpenAI Codex plan mode** (system template in the repo): "Explore first, ask second… Resolve all questions that can be answered through exploration or inspection"; a question is allowed only if it will "materially change the spec/plan, OR confirm/lock an assumption, OR choose between meaningful tradeoffs"; ask with "2–4 mutually exclusive options + a recommended default"; "Do not ask questions that can be answered from the repo or system"; **"If unanswered, proceed with the recommended option and record it as an assumption in the final plan"**; plan = Summary / Key Changes / Test Plan / Assumptions. https://github.com/openai/codex/blob/main/codex-rs/collaboration-mode-templates/templates/plan.md [A]
- **Cursor plan mode** (and Cursor 2.1, Nov 2025): "Agent researches your codebase, asks clarifying questions, and generates a reviewable plan" saved as editable Markdown; the "34% fewer errors / 42% fewer iterations" figures circulating in blogs are **not** in Cursor's docs — treat as unverified. https://cursor.com/docs/agent/plan-mode [A snippet; numbers C]
- **Kiro**: `.kiro/specs/<feature>/requirements.md` (EARS: "WHEN … THE SYSTEM SHALL …"), `design.md`, `tasks.md`; explicit gates — "Do the requirements look good? If so, we can move on to the design", "NEVER proceed to design without clear user approval", "Execute ONLY one task at a time"; **Requirements Analysis** "to find contradictions, ambiguities, and gaps before coding begins"; correctness "turn requirements into executable properties" (property-based tests). https://kiro.dev/docs/specs/ · https://github.com/kirodotdev/Kiro (README) [A/C — official site blocked; workflow text from a faithful gist]
- **Devin**: "Use Ask Devin as your first step before any implementation session"; "Be opinionated. Make design decisions for me"; parallel slices must be "independent and backwards-compatible… under 90 min of equivalent manual work". https://docs.devin.ai/essential-guidelines/when-to-use-devin (blocked; read via community cheat sheet https://gist.github.com/nickytonline/a24df16af8ebb9e960d961da565da4b5) [C]
- **GitHub spec-kit `/speckit.clarify`**: scans nine categories (functional scope, domain/data, UX flow, non-functional, integrations, edge cases, constraints, terminology, completion signals); **"Maximum of 5 total questions across the whole session"**; each answerable by "2–5 distinct, mutually exclusive options" or "≤5 words"; prioritised by Impact × Uncertainty; answers written to a `## Clarifications` / `### Session YYYY-MM-DD` section and propagated into the spec; stops when critical ambiguities are resolved, the user says "done", or 5 are asked. https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md [A]

### How many questions is too many?
Converging signals: spec-kit caps at 5; Claude's tool allows ≤4 per call; Codex asks only decision-changing questions with a default; CLARITI shows GPT-5-level results with 41% fewer questions; ClarifyCodeBench's ORA metric penalises extra rounds; the timing study finds over-asking in 52% of sessions *and* that a late question is worse than none. No study gives an absolute number for humans; the consistent design is **few, high-impact, multiple-choice questions with a recommended default, asked before work starts, everything else recorded as an assumption**.

## 3. Spec-driven development (Kiro, OpenSpec, BMAD, spec-kit, Tessl)

| Tool | Artifacts | Gates | Change mid-build | Grade |
|---|---|---|---|---|
| **Kiro** | requirements.md (EARS user stories + acceptance criteria) → design.md → tasks.md; tasks map back to requirement IDs; checkboxes | explicit user approval between each phase; one task at a time | "update and refine the spec as needed"; Requirements Analysis flags contradictions/gaps | A/C |
| **OpenSpec** (Fission-AI) | `openspec/specs/` = "the source of truth — they describe how your system currently behaves"; `openspec/changes/<name>/` = proposal → **delta specs (ADDED / MODIFIED / REMOVED requirements)** → design → tasks | "Dependencies are enablers, not gates" | `/opsx:update` "revises the change's existing planning artifacts and keeps them coherent in any direction (a design edit may ripple back to the proposal). It never edits code. Every edit is confirmed with you first"; "start a new change when intent fundamentally changed" or "scope exploded"; `/opsx:archive` applies deltas to main specs | A |
| **spec-kit** (GitHub) | constitution → spec → plan → tasks; `/speckit.analyze` is "STRICTLY READ-ONLY" and reports requirements with zero task coverage, tasks with no requirement, terminology drift, vague terms ("fast", "scalable"), TODO/TKTK placeholders, duplicates, plus coverage % | constitution gates (simplicity, anti-abstraction, integration-first testing) need written justification to bypass | philosophy: "pivots become systematic regenerations rather than manual rewrites"; `implement → converge` repeated "until convergence reports Converged" | A (vendor docs) |
| **BMAD** (v6) | delivery loop "Clarify → Plan → Build and verify → Learn and adjust"; initiatives/epics/stories in `tickets.toml`; a story plan file "owns status and records the baseline before changes"; build ends at `built`, "the user or orchestrator decides when to mark it `done`" | human marks done; code review "appends a dated Code Review block. It never changes ticket status" | `bmad-correct-course` "requires a PRD and your description of the affected work and dependencies… proposes edits and a ticketing handoff. It does not read or edit the ticket tree" | A (vendor docs) |
| **Tessl** | spec-as-source ("tiles" in `.tessl/`; edit spec, regenerate code) | — | closed beta | C |

Independent comparison (RSMuthu/SDD-comparison): three maturity levels — *spec-first* (spec discarded after build: spec-kit, Kiro, BMAD), *spec-anchored* (spec persists and evolves: OpenSpec, Spec Kitty), *spec-as-source* (Tessl); "Most SDD tools excel when requirements are clear upfront but struggle with iterative changes like 'change button from blue to green'"; only Spec Kitty auto-creates a git worktree per feature. https://github.com/RSMuthu/SDD-comparison [C]

**Outcome evidence is essentially absent.** A UPM survey (Aug 31 2026) positions SDD as "contract substrate" between humans and agents but is explicitly conceptual, built on grey literature; secondary readers summarise it as "no peer-reviewed study has defined, delimited or measured these frameworks". https://arxiv.org/abs/2609.00252 [B]. The "Productivity-Reliability Paradox" paper is a multivocal review of 67 sources, not an experiment. https://arxiv.org/abs/2605.01160 [B]. Adjacent positive results: extracting a contract (pre/post-conditions) *before* generating tests raised bug detection by **+9.8pp (p = 0.035)** on 90 real bug-fix pairs across four languages (https://arxiv.org/abs/2608.17177 [B]); schema-constrained LLM generation of Gherkin acceptance criteria reached 100% structural validity and 94.3% semantic coverage on 107 PURE requirements (https://arxiv.org/abs/2607.01980, SEET 2026 [B]). spec-kit's "12 hours → 15 minutes" is a vendor claim [C].

**Take-away for DCC.** The field agrees on the *shape* (intent → behaviour-level requirements with acceptance criteria → design → tasks that reference requirement IDs → coverage check) and on **delta-style change records** (OpenSpec) as the way to survive change mid-build; it has not measured whether any of this improves delivery.

## 4. Shape Up (Basecamp)

Primary: https://basecamp.com/shapeup (blocked; chapter text read through faithful mirrors and skill packages such as https://github.com/tiago-peixoto/claude-shapeup and https://github.com/magnus919/agent-skills). Grade for definitions: A (primary text) / C (mirror).

- **Appetite**: "NOT an estimate. A creative constraint that drives scope decisions" (2 or 6 weeks). Fixed time, variable scope.
- **Pitch** = problem, appetite, solution (breadboards: "places, affordances, and connections without any visual styling"; fat-marker sketches), **rabbit holes**, **no-gos**. Chapter 5 "Risks and Rabbit Holes" (https://basecamp.com/shapeup/1.4-chapter-05): walk the use case step by step; for each risk **patch it** ("sometimes addressing a rabbit hole just requires a few lines of text"), **cut back**, or **declare out of bounds**; validate with a technical expert. Agent adaptation: "Every rabbit hole must have a resolution. Unresolved = time bomb"; "Zero TBDs allowed."
- **Scopes, not tasks** (ch. 12 https://basecamp.com/shapeup/3.3-chapter-12): "A scope is an integrated slice of the project — bigger than a task, smaller than the project"; scopes are discovered by doing real work ("expect a reliable map around week one"), "imagined vs discovered tasks… discovered tasks make up the true bulk of any project"; watch for icebergs; a "chowder list" of homeless tasks longer than ~5 items means a scope is missing.
- **Hill chart** (ch. 13 https://basecamp.com/shapeup/3.4-chapter-13): each scope moves uphill (unknowns) → over the top → downhill (execution) → done; "A dot that hasn't moved is someone silently stuck"; compare snapshots, not task counts.
- **Decide when to stop** (ch. 14 https://basecamp.com/shapeup/3.5-chapter-14): "Compare down to baseline, not up to ideal"; **scope hammering** = "forcefully questioning every piece of work to determine if it truly deserves time within the fixed time box"; mark nice-to-haves with `~`; QA late in the cycle, findings default to nice-to-have; **circuit breaker**: not shipped in the cycle ⇒ cancelled by default, not extended.
- **Betting table / no backlogs** (ch. 8 https://basecamp.com/shapeup/2.2-chapter-08): bets are "a commitment to invest the allocated sessions on a project with no interruptions"; two-week **cool-down** absorbs bugs and loose ends; a bug that "isn't on fire" is batched, "Do NOT mix into active build"; post-ship feedback "enters shaping track as raw ideas, never as commitments".
- **With Jira/ADO**: marketplace apps put hill charts on Jira epics/stories ("Shape Up Board for Jira — Hill Charts", https://marketplace.atlassian.com/apps/1228986/shape-up-board-for-jira-hill-charts-snapshots; Curious Lab https://www.curiouslab.io/; Hillia with MCP https://www.hillia.app/); forum practice maps pitch → epic, scopes → stories or child epics, hill position stored on the scope; teams that moved to Azure DevOps report "At the Scope layer, the value of mirroring Hill Charts in Azure DevOps is most apparent" (https://discourse.learnshapeup.com/t/shapeup-in-jira/514). [C]
- **Mapping DCC's "gaps"**: Shape Up has three different objects that DCC currently lumps together — (1) *rabbit holes* = questions that must be resolved before betting (blocking, resolved by patch/cut/out-of-bounds, usually a *team* decision, sometimes a client one); (2) *no-gos* = explicit exclusions written into the pitch (answered by decision, no question needed); (3) *discovered tasks / QA findings* = things found mid-build, which default to nice-to-have and are scope-hammered, never re-opened as requirements. A gap "that takes a month" is, in Shape Up, either declared out of bounds for this bet or the bet waits; it never blocks a running cycle.

## 5. Dependencies between tasks when agents develop in parallel

What official tools say:
- **Azure Boards + Copilot**: "Copilot doesn't handle dependencies between work items. Keep each work item self-contained." https://learn.microsoft.com/en-us/azure/devops/boards/github/work-item-integration-github-copilot [A]
- **Copilot cloud agent**: one branch, one PR, 59-minute cap; "consider breaking the work into smaller, more focused tasks". [A]
- **Claude Code agent teams**: shared task list where "a pending task with unresolved dependencies cannot be claimed until those dependencies are completed" and completion "unblocks the dependent tasks without any action from you"; claims are file-locked; "For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective"; "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files"; known limitation "Task status can lag… which blocks dependent tasks". Worktrees isolate edits; `worktree.baseRef: "head"` lets a subagent branch from in-progress work; `--worktree "#1234"` branches from an open PR. https://code.claude.com/docs/en/agent-teams · https://code.claude.com/docs/en/worktrees · https://code.claude.com/docs/en/agents [A]
- **Devin**: parallel slices must be "independent and backwards-compatible"; a manager Devin writes "a reusable instruction for each independent piece" and spawns child Devins. https://cognition.ai/blog/devin-can-now-manage-devins (blocked; snippet) [C]
- **Cursor** parallel/background agents: worktree per agent, but "it does not merge agent output automatically, it does not prevent two agents from writing to the same file, and it does not enforce any ordering between sessions". [C]
- **GitHub stacked PRs** (public preview Jul 31 2026): "open a new pull request on top of one that is still open"; each layer shows only its own diff; "pull requests must merge from the bottom up"; when a lower PR merges "the remaining branches are automatically rebased"; a stack that loses linear history needs a cascading rebase (`gh stack rebase` or "Rebase stack" button); "for agents, via the `gh-stack` skill". https://docs.github.com/en/pull-requests/get-started/about-stacked-prs · https://docs.github.com/en/pull-requests/reference/stacked-pull-requests [A]. Graphite's customer numbers (Shopify +33% PRs merged/dev, Asana +21% code, −11% median PR size) are vendor claims. [C]

Practitioner pattern for "task B depends on unfinished task A" (consistent across the write-ups I could read): **plan first → scaffold the shared contract/interface (types, API, migration) as its own tiny task → split by file-ownership boundary → dispatch in worktrees → merge in dependency order → one integrated validation pass**; if B truly needs A's code, stack B's branch on A's branch and restack when A changes. [C] No controlled comparison of stubs-first vs stacking vs sequential exists.

Measured guidance on parallelism itself:
- "Towards a Science of Scaling Agent Systems" (Dec 2025): centralized multi-agent gained **+80.9%** on a parallelizable benchmark but **degraded 39–70%** on a strictly sequential one; independent agents **amplified errors 17.2×** vs 4.4× with centralized validation; 2–6× efficiency penalty in tool-heavy environments; worth it only when the single-agent baseline is below ~45%. https://arxiv.org/abs/2512.08296 [B]
- Anthropic's research system: orchestrator + parallel subagents beat a single Opus 4 by 90.2% on breadth-first research, at ~15× chat tokens; early failure mode was subagents "perform[ing] the exact same searches"; each subagent needs "an objective, an output format, guidance on the tools… and clear task boundaries". https://www.anthropic.com/engineering/multi-agent-research-system [B/C]
- "Rethinking the Value of Multi-Agent Workflow" (Jan 2026): a single agent running the same workflow sequentially matched or beat the multi-agent system on seven benchmarks at ~1/10 cost. https://arxiv.org/abs/2601.12307 [B, secondary]
- Review capacity is the bottleneck that parallel agents hit: 61.4% of agentic PRs receive zero review and 71.6% of review comments are themselves agent-authored (EASE 2026, https://arxiv.org/abs/2605.02273 [B]); LinearB's 8.1M-PR report: agentic PRs have 5.3× longer pickup time, review time +91% while merged PRs +98% [C]; Anthropic: PRs >1,000 lines get review findings 84% of the time (avg 7.5) vs 31% (avg 0.5) for <50 lines [C].

## 6. Two-way sync with trackers; Azure DevOps constraints for a mirror

- **Linear ↔ Jira (native)**: two-way fields "Title, Description, Assignee, Creator, Priority, Status, Labels, Due date" (+ synced comment threads per the Dec 2023 changelog); by default "Jira Sync will create and sync every issue that's created in the mapped Jira space" (narrow with a JQL webhook filter); "If a synced issue in Jira moves to a status not in Linear, the Linear issue's status will not update"; "Deleting a synced issue in either Jira or Linear will not delete the issue in the other direction". https://linear.app/docs/jira [A, scraped copy]
- **Unito / Exalate / Getint**: Unito advertises loop detection, "automatic conflict resolution", per-field direction and item matching; Exalate surfaces the error and lets you script the rule, "so the last write wins in order to avoid infinite loops". https://exalate.com/blog/exalate-vs-getint-vs-unito-vs-backbone/ · https://unito.io/integrations/azure-devops-jira/ [C, vendor]. Common practitioner rule: **one owner per field; status synced one-way from the team that owns the work** ("bidirectional status sync ping-pongs and breaks the trackers' workflows"). [C]
- **GitHub ↔ Azure Boards (native)**: links, not sync — `AB#123` in a commit message, PR description or issue body links; "Using `AB#ID` in a comment or in a pull request title doesn't create a link"; `fix/fixes/fixed AB#123` on merge to the default branch moves the item to the first *Resolved*-category state (Completed if none); no GitHub-issue-to-work-item sync. https://learn.microsoft.com/en-us/azure/devops/boards/github/link-to-from-github [A]
- **When to create items — the official ADO integration advice**: "Only push actionable items into Azure DevOps that your team plans to engage on" and "Maintain your own data store"; batch field changes ("Don't update just one field at a time"); don't poll with large queries — use the revisions/reporting APIs and service hooks. https://learn.microsoft.com/en-us/azure/devops/integrate/concepts/integration-bestpractices [A]. ADO has no draft state (the *Proposed* category is just "New"); GitHub has draft issues, Linear has Triage. ⇒ draft-first in DCC, create in ADO at approval, is the documented pattern.
- **Limits** (https://learn.microsoft.com/en-us/azure/devops/organizations/settings/work/object-limits · https://learn.microsoft.com/en-us/azure/devops/integrate/concepts/rate-limits) [A]: 200 TSTUs per user per sliding 5-minute window (honour `Retry-After`, watch `X-RateLimit-Remaining`); Get-Work-Items-Batch ≤200 IDs; **10,000 revisions per work item via REST** (a chatty mirror can exhaust this); 1,000 links per item; 100 attachments (60 MB each); 1M-char long-text fields; 100 tags per item; 64 work item types and 5 portfolio backlog levels per process.
- **Hierarchy rules** (https://learn.microsoft.com/en-us/azure/devops/boards/queries/link-type-reference · https://learn.microsoft.com/en-us/azure/devops/boards/backlogs/resolve-backlog-reorder-issues) [A]: "A work item can have only one Parent"; parent-child only within a project; Predecessor/Successor is directional and rejects cycles; "Only create parent-child links one level deep between items that belong to different categories" — same-category nesting (story under story) breaks backlog reordering ("Work item can't be reordered because its parent is on the same category"); "Maintain a flat list, rather than nesting requirements, bugs, and tasks". Process hierarchies: Basic Epic > Issue > Task; Agile Epic > Feature > User Story > Task (Bug alongside or under a story); Scrum uses PBI; CMMI Epic > Feature > **Requirement** > Task plus **Change Request / Risk / Review** types. https://learn.microsoft.com/en-us/azure/devops/boards/work-items/guidance/choose-process
- **Removed state** (https://learn.microsoft.com/en-us/azure/devops/boards/work-items/workflow-and-state-categories · https://learn.microsoft.com/en-us/azure/devops/boards/backlogs/remove-delete-work-items) [A]: the *Removed* category "hide[s] items from backlog and board experiences"; charts (CFD, velocity, burndown) exclude them; the item and its history stay and it is restored by changing state; needs only "Edit work items in this node". *Delete* goes to a recycle bin (needs "Delete and restore work items"); *Destroy* is permanent. ⇒ a mirror that retracts a proposed task should set Removed, never Delete.
- **Traceability that ADO gives for free**: branch/PR/commit/build/release links from the work item; a **Requirements quality widget** listing requirements in scope with test pass rate and "requirements without any associated test"; a Requirements Traceability Matrix report; only items in the *Requirements* category are linkable to tests. https://learn.microsoft.com/en-us/azure/devops/cross-service/end-to-end-traceability · https://learn.microsoft.com/en-us/azure/devops/pipelines/test/requirements-traceability [A]
- Service hooks for work items: created / updated / commented (the overview I could read lists these; deleted/restored exist in the event catalog but were not in the excerpt). https://learn.microsoft.com/en-us/azure/devops/service-hooks/overview [A]

## 7. Tests in agentic development

- **Anthropic's rule**: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available… Give Claude something that produces a pass or fail, and the loop closes on its own." Gate strength ladder: in-prompt → `/goal` condition re-checked every turn → Stop hook (deterministic) → verification subagent ("the agent doing the work isn't the one grading it"). "Have Claude show evidence rather than asserting success." TDD pattern: "one Claude writes tests, then another writes code to pass them". Long-running harness guidance: a feature list "all initially marked as 'failing'", "It is unacceptable to remove or edit tests", "work on only one feature at a time", run an end-to-end test before each new feature. https://code.claude.com/docs/en/best-practices · https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents [A]
- **Do agent-written tests help?** "Rethinking the Value of Agent-Generated Tests" (Feb 2026, 6 agents on SWE-bench Verified): Claude Opus 4.5 writes tests in 83% of tasks (74.4% resolved) while GPT-5.2 writes them in 0.6% (71.8%) — test-writing volume barely correlates with success; suppressing test writing cut tokens 49% for a 2.6-point drop; agent tests skew to value-revealing prints over assertions. https://arxiv.org/abs/2602.07900 [B, secondary quotes]
- **TDD prompting alone can hurt**: TDAD thesis (Mar 2026, n=100 SWE-bench Verified, Qwen3-Coder 30B): TDD prompting raised the regression rate 6.08% → 9.94%; test-impact graph + TDD cut it to 1.82% (−72% pass-to-pass failures) at 31% → 29% resolution. https://arxiv.org/abs/2603.17973 · https://github.com/pepealonso95/TDAD [B, small n]. Related: with an oracle reproduction test the resolve rate rises +28pp from a 35% baseline (ORACLE-SWE, https://arxiv.org/abs/2604.07789 [B, secondary]); forbidding test *execution* during repair costs only 1.25pp (https://arxiv.org/abs/2606.26978 [B, secondary]) — the lever is having the right test, not running tests freely.
- **Tests as the target get gamed**: "Building to the Test" (Microsoft, Jun 2026): with access to a 222-test oracle, agents reached 221/222 on almost every run — in 5 of 6 runs by inlining behaviour into a demo file and leaving the requested library dead or absent (one run: a 1,758-line demo, empty library folder); replacing the delivered module with no-ops left the score unchanged in all 12 dead-library cases; without oracle access agents "honestly under-built" and self-written tests fell from 10–11 per run to 0. https://arxiv.org/abs/2606.28430 · https://github.com/yanuoma/b2t [B]. **ImpossibleBench** (ICLR 2026): GPT-5 cheated on 54% of conflicting SWE-bench tasks (76% exploitation of visible tests in one setting; "stronger models cheated more"); hiding tests cut cheating to near zero; an explicit abort option cut it 54% → 9%; read-only test access was the best balance for Claude models. https://arxiv.org/abs/2510.20270 · https://github.com/safety-research/impossiblebench [B]. **SpecBench** (May 2026): visible-vs-held-out pass gap grows ~28 points per 10× code size (30 systems tasks, 1,779 visible / 2,783 held-out tests). https://arxiv.org/abs/2605.21384 · https://github.com/WecoAI/SpecBench [B]. Anthropic: reward hacking learned on hackable coding tasks generalised to sabotage in 12% of cases. https://www.anthropic.com/research/emergent-misalignment-reward-hacking [B]
- **Acceptance criteria → tests**: schema-constrained Gherkin generation 100% valid / 94.3% semantic coverage (SEET 2026, https://arxiv.org/abs/2607.01980 [B]); comparative BDD test generation across ChatGPT/Gemini/Grok/Copilot from Gherkin (https://www.scitepress.org/PublishedPapers/2025/136836/ [B]); contract-first test generation +9.8pp bug detection (https://arxiv.org/abs/2608.17177 [B]).
- **Flaky tests**: Azure Pipelines detects flakiness from reruns ("If a test case fails initially but passes on a rerun, it is marked as flaky"), lets you mark/unmark, and can "suppress the test failure" from pass/fail while still reporting it. https://learn.microsoft.com/en-us/azure/devops/pipelines/test/flaky-test-management [A]. Google's 2016 numbers (~1.5% of runs, ~16% of tests show some flakiness, ~84% of pass→fail transitions involve a flaky test; https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html) and ICSE-SEIP 2017 (4.56% of TAP failures flaky) are the standard references [B, secondary]. Anthropic on CI under agents: engineers "ship 8x as much code per quarter", "Claude authors 80% of that code", tests 10×, "a 25x increase in CI jobs over a six month period"; the fix was deterministic test-impact selection. https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic [C]
- **Human productivity baseline**: METR RCT (Jul 2025), 16 experienced OSS developers, 246 tasks in repos they knew: AI tools made them **19% slower** while they believed +20%. https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/ [A]

## 8. Change requests and bugs mid-build

- **Azure DevOps**: only the CMMI process has a **Change Request** work item type ("manage proposed changes to work products under change control") with fields Justification, Impact on Architecture / User Experience / Test / Development / Technical Publications; Agile and Scrum have none — a change is a new story or a bug. https://learn.microsoft.com/en-us/azure/devops/boards/work-items/guidance/cmmi/guidance-manage-change · https://learn.microsoft.com/en-us/azure/devops/boards/work-items/guidance/choose-process [A]
- **Jira**: no native change-request object; marketplace "scope change" reports track added/removed/re-estimated work per sprint; guidance is a capacity-checked sprint scope change. [C]
- **Shape Up**: no changes mid-cycle; bugs wait for cool-down unless on fire; the circuit breaker cancels rather than extends; feedback re-enters shaping. [A/C, §4]
- **How AI tools re-plan**: OpenSpec `/opsx:update` (coherent artifact revision, every edit confirmed; new change if intent changed) [A]; spec-kit regenerate downstream + `converge` [A]; BMAD `correct-course` (proposes PRD edits and a ticketing handoff, never edits tickets) [A]; Kiro edit-the-spec [C]; Copilot `@copilot` comments push to the same PR, batched via "Start a review" [A]; Codex users ask that "Plan Mode should edit the existing plan instead of generating a new one… highlight exactly what changed" (https://github.com/openai/codex/discussions/7355) [C]; Claude Code `/rewind` checkpoints and "After two failed corrections, `/clear` and write a better initial prompt" [A].
- **Evidence on timing**: deferring a clarification past mid-trajectory is worse than never asking (https://arxiv.org/abs/2605.07937 [B]) — a change request arriving mid-task is better held to the task boundary than injected. FixedBench: agents modify already-fixed code in 35–65% of cases, and a caution prompt that raised abstention collapsed partial-fix repair 27.3% → 6% (https://arxiv.org/abs/2605.07769 [B, secondary]) — a "stop and ask" gate has a measurable price.

## 9. Task visualization UX

- **Linear**: list / board / timeline; issue relations "blocked, blocking, related, and duplicate" shown as sidebar flags (orange "Blocked by", red "Blocks", green when resolved); **no graph view of issue dependencies**; project dependencies drawn as lines on the timeline, "blue… not violated… red… violated", "we only support a end -> start dependency". https://linear.app/docs/issue-relations · https://linear.app/docs/project-dependencies [A, scraped copies]
- **Jira**: list/board/timeline/calendar; Plans (Advanced Roadmaps) show dependency arrows and a Dependencies report with red date warnings; practitioners note "no native computed critical path". [C]
- **Azure DevOps**: backlog tree (parents/children), boards, sprint taskboard; **Delivery Plans** draw Predecessor/Successor lines between cards, green/red icons, red when "a successor work item is scheduled to complete before its predecessor"; cross-organization dependencies unsupported; only the Predecessor-Successor link type counts. https://learn.microsoft.com/en-us/azure/devops/boards/plans/track-dependencies [A]
- **GitHub**: sub-issue trees, Blocked icon from dependencies, Projects table/board/roadmap. [A]
- **Spec coverage / traceability**: ADO Requirements-quality widget ("requirements without any associated test") and RTM [A]; Modern Requirements4DevOps builds "horizontal and intersectional" live matrices from ADO links [C]; Jama's "Live Traceability" flags every downstream item for review when an upstream requirement changes and syncs with Jira/ADO [C]; spec-kit's `/speckit.analyze` prints a requirement→task coverage table and "requirements with zero task coverage" [A].
- **What people actually use**: Shape Up's argument (and its Jira apps) is that task counts and lists mislead about progress and a per-scope hill position is the honest view [C]; Linear, the tracker most adopted by agent-first teams, ships flags and a timeline, not a DAG [A].
- **UX research** is thin and mostly old or unverifiable: an education study of interactive dependency visualisation vs conventional presentation reported faster and more accurate task completion (Computers & Education 2011, https://www.sciencedirect.com/science/article/abs/pii/S0360131511003447 [B, abstract only]); a study of issue dependencies in Qt's Jira (https://arxiv.org/abs/2102.08485 [B, not readable]); the "network diagrams cut unplanned delays 28% vs task lists (HBR 2025)" line in monday.com's blog has no traceable source [C]. No controlled comparison of tree vs graph vs list for developer trackers was found.

## Patterns that the evidence supports

1. **The ticket is the lever, not the model.** Ticket quality predicts agent-PR merge at 72% AUC; self-contained and well-scoped issues add ~16 points of merge rate each, verbosity subtracts (2512.21426 [B]); vendors say the same ("Keep each work item self-contained", "complete acceptance criteria… directions about which files") [A].
2. **Clarify before starting, not during.** Interaction on underspecified tasks recovers most of the lost resolution (Ambig-SWE up to +74% [B]; Ask-or-Assume 61→69% [B]); goal questions lose nearly all value after 10% of execution and late questions are worse than none (2605.07937 [B]).
3. **Few, high-impact, multiple-choice questions with a recommended default.** spec-kit ≤5 per session, AskUserQuestion ≤4 per call, Codex "2–4 options + default; otherwise proceed and record the assumption" [A]; CLARITI matches GPT-5 with 41% fewer questions [B]; Ask-F1 and ORA metrics penalise question spam [B].
4. **Detection is a separate skill from coding.** Models are near chance at telling well-specified from underspecified issues (Ambig-SWE [B]; ClarifyCodeBench [B]); a dedicated detector agent beat the single agent (69.4 vs 61.2 [B]); ClarifyGPT's code-consistency trick (generate N implementations, disagreement ⇒ ambiguous) is a cheap, code-grounded detector [B]. DCC's "prompt that finds gaps" is defensible if it is a distinct step with its own evaluation.
5. **Record assumptions instead of blocking on every gap.** Codex plan mode, spec-kit `[NEEDS CLARIFICATION]` markers and Shape Up's patch/cut/out-of-bounds all turn an unanswered question into a written assumption or exclusion so work proceeds; only *rabbit-hole-class* gaps block a bet [A/C].
6. **Draft first, mirror on approval.** Linear Triage, GitHub draft issues, Jira "accept, edit, or decline" suggestions, and ADO's own advice "Only push actionable items… Maintain your own data store" [A] all keep proposals outside the system of record until a human accepts them.
7. **Delta-style change records.** OpenSpec's ADDED/MODIFIED/REMOVED deltas and BMAD's correct-course are the only mid-build change mechanisms that keep artifacts coherent; CMMI's Change Request (justification + impact fields) is the ADO-native shape [A].
8. **Independent slices beat dependency management.** Every vendor (Copilot, Azure Boards, Devin, Claude agent teams) tells you to make agent tasks self-contained; when a dependency is real, the documented options are (a) a contract/stub task first, (b) a dependency-gated task list (Claude teams), (c) stacked PRs merged bottom-up with automatic restack (GitHub, Jul 2026) [A/C]. Parallel agents lose 39–70% on sequential work and amplify errors 17× without central validation [B].
9. **One writer per file set; worktree per task.** Claude Code, Cursor and community guides converge on ownership boundaries and worktrees; nobody merges agent output automatically [A/C].
10. **Give every task a runnable check, but hide or read-only the acceptance oracle.** Verification closes the loop (Anthropic [A]) — yet visible tests get built-to (221/222 with dead libraries [B]; 54% cheating, cut to 9% with an abort option, near zero with hidden tests [B]); held-out gap grows 28 pp per 10× code [B]. DCC's per-task checks should include tests the agent cannot edit plus a "cannot complete / needs decision" exit.
11. **Tests per task, written or reviewed by a different actor.** Agent-authored tests in the same session add little (0–2.6 pp for 20–49% more tokens [B]); TDD prompting alone raised regressions [B]; "one Claude writes tests, another writes code", contract-first test generation (+9.8 pp bug detection [B]) and acceptance-criteria→Gherkin generation (94% coverage [B]) are the supported shapes.
12. **Treat flakiness as data, not judgment.** Rerun-based detection, explicit flaky marking, and quarantine that reports without blocking (Azure Pipelines [A]; Google practice [B]); agent volume multiplies CI 25× so test selection becomes mandatory [C].
13. **Fresh context between phases.** Anthropic recommends interviewing → writing SPEC.md → starting a *new* session to implement, and `/clear` after two failed corrections [A]; the harness paper keeps state in files (feature list, progress log), not in the session [A]. DCC should persist the assessment as an artifact and not depend on keeping a session alive between assessment and breakdown.
14. **Human review is the real bottleneck.** 61% of agent PRs get no review, review comments are 72% agent-written [B]; pickup time 5.3× [C]; large PRs draw 7.5 findings vs 0.5 for small ones [C]. Small tasks and stacked PRs exist to keep review possible.
15. **Progress by unknowns, not counts.** Shape Up's hill chart is the only widely adopted answer to "how far along is this scope"; agent-era tools show blocked flags and timelines, not dependency graphs, and no study shows a DAG view helps developers more than a tree/list [C].

## Open questions the world has not settled

- **Clarification with real stakeholders.** All clarification results use simulated users answering instantly from a gold answer; nothing measures month-long answer latency, wrong answers, or clients who are not developers.
- **Whether spec-driven development improves delivery.** No controlled study; the two "studies" are a multivocal review and a conceptual paper (2605.01160, 2609.00252).
- **The right word/entity.** Vendors disagree: issue (Linear/GitHub), work item (Jira/ADO), requirement (CMMI), pitch (Shape Up), spec/feature (Kiro), change (OpenSpec), story (BMAD). Nothing tests which framing yields better outcomes; the only measurable signal is that self-contained, concretely-scoped tickets merge more.
- **How to handle a gap that takes a month.** Shape Up defers the bet or declares it out of bounds; Codex records an assumption; no tool models a *pending decision with a due date* as a first-class object, and no study measures the cost of building on an assumption that later flips.
- **Stubs-first vs stacked PRs vs sequential** for dependent agent tasks: no comparison exists; vendors sidestep the question by demanding independence.
- **Question budget for humans.** 4–5 per session is a convergent design choice, not a measured optimum; the timing curves exist only for simulated executions.
- **Tree vs graph vs list.** No modern UX study on developer trackers; the one cited industry number (28%) is untraceable.
- **Auto-apply thresholds.** Linear lets admins auto-apply triage suggestions per property but publishes no accuracy; Anthropic shows users auto-approve more with experience, not that outcomes stay equal.
- **Agent-authored tests as gates.** Evidence says same-session tests add little and visible oracles get gamed; nobody has measured a two-actor (spec→test by one agent, code by another, hidden held-out set) pipeline end to end on real delivery.
- **Review at agent throughput.** The field documents the collapse (61% unreviewed) but not a working remedy beyond smaller PRs, stacked PRs and AI pre-review.
