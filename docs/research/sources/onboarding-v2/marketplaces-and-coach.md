**How to judge trust/safety (synthesis, [C] from [A] sources above):**
1. *Namespace / org ownership* is the only universally available trust signal: reverse-DNS or vendor `io.github.<vendor>` in the MCP registry; `github.com/<vendor>` marketplace sources; Docker-built tier.
2. *Pinned revision*: the official Claude marketplace pins every git source to a `sha`; the MCP registry has versions; Docker has `source.commit`. Prefer entries you can pin.
3. *Permissions requested*: MCP registry `environmentVariables[].isSecret`/`isRequired` and `remotes` tell you what credentials a server wants; Docker `config.secrets`; plugin `details` shows hooks/MCP servers/agents. Read-only flags exist on most vendor servers (see table 1.2).
4. *Prompt-injection / tool-poisoning*: instructions hidden in tool descriptions, indirect injection via fetched data, and "rug pull" (a trusted server's tool descriptions change after approval) are documented attack classes (Invariant Labs, Simon Willison, CSA) [B]. Mitigations: show and diff tool descriptions across sessions, scan configs (Invariant `mcp-scan`), limit to read-only toolsets, and keep the tool count small. Claude Code's plugin evals never start real MCP servers unless `--allow-real-servers` — mocks are the default — which is itself a safety pattern. [A]
5. *Context cost*: see 1.3.

### 1.3 MCP context-cost caveats [A]

- Anthropic engineering ("Advanced tool use"): five servers — GitHub 35 tools ≈ 26K tokens, Slack 11 ≈ 21K, Sentry 5 ≈ 3K, Grafana 5 ≈ 3K, Splunk 2 ≈ 2K — "58 tools consuming approximately 55K tokens before the conversation even starts"; adding Jira (~17K) pushes past 100K; Anthropic's own internal setup hit 134K. The Tool Search Tool (`defer_loading: true`) cut that by 85% and raised tool-selection accuracy (Opus 4: 49→74%; Opus 4.5: 79.5→88.1%). Guidance: use tool search when definitions exceed ~10K tokens; keep the 3–5 most-used tools always loaded, defer the rest; it is "less beneficial when small tool library (<10 tools)". https://www.anthropic.com/engineering/advanced-tool-use
- Claude Code: MCP tool search is on by default (off with `ENABLE_TOOL_SEARCH=false`, custom `ANTHROPIC_BASE_URL`, or pre-4.5 models); remote servers can use a discovery cache; output over 10K tokens warns and over `MAX_MCP_OUTPUT_TOKENS` (default 25K) is spilled to a file. https://code.claude.com/docs/en/mcp
- Best-practices doc: "CLI tools are the most context-efficient way to interact with external services" (prefer `gh`, `aws`, `sentry-cli`); put rarely-needed knowledge in skills, which load on demand, not in CLAUDE.md. https://code.claude.com/docs/en/best-practices
- Vendor servers all ship a tool-limiting switch — ADO `-d`, GitHub `--toolsets/--tools/--read-only`, Azure `--mode/--namespace`, Playwright `--caps`, Grafana `--disable-*`, Salesforce `--toolsets`, Terraform `--toolsets`, K8s toolsets + `read_only`. An onboarding recommendation should always come with the minimal toolset flag, not the default. [C]

**Instruction-file bloat/decay — the evidence** (all arXiv, blocked; numbers via search summaries and secondary write-ups, [B]):
- *Evaluating AGENTS.md* (Gloaguen et al., arXiv 2602.11988): context files "do not generally improve task success rates, while increasing inference cost by over 20% on average"; LLM-generated context files reduced success ≈3%; holds across LLMs, agents, and both developer-written and generated files.
- *Do Context Files Help Coding Agents? A Two-Agent Ablation* (arXiv 2607.27250): Claude Code + Codex, 17 tasks, 3 repos, 288 runs; context strategy (none / always-on / selective) does not measurably move correctness (bounded ≤10–15 pp); failures are implementation-skill failures, not missing repo knowledge; task difficulty is agent-specific, which explains contradictory single-agent studies.
- *On the Impact of AGENTS.md on Efficiency* (Lulla et al., JAWS 2026): AGENTS.md lowers wall-clock time and output tokens — an efficiency, not a correctness, effect.
- *Instruction Adherence in Coding Agent Configuration Files* (McMillan, arXiv 2605.10039): 1,650 Claude Code sessions, 16,050 observations; file size (25–500 lines), instruction position, single vs split files, and a conflicting instruction produced **no detectable effect** after correction; the dominant effect was *within-session drift*: ≈5.6% lower odds of compliance per additional generated function.
- *Agent READMEs* (Chatlatanagulchai et al., arXiv 2511.12884): 2,303 context files in 1,925 repos; content is mostly functional (tests 75.9%, implementation 70.8%, architecture 68.1%), rarely security (14.8%) or performance (14.5%).
- Anthropic's own docs (above, [A]) assert the opposite direction on length: "Longer files consume more context and reduce adherence"; "Bloated CLAUDE.md files cause Claude to ignore your actual instructions".
- Pruning methods actually documented: `/doctor` proposes derivable-content cuts [A]; skill-creator and `claude plugin eval` run the same tasks with/without a component and keep it only if Δ>0 [A]; Copilot's 28-day expiry + citation re-verification [B]; the practitioner rule "delete the rule, re-run the evals, keep the deletion if the score holds" is not documented by any vendor as a product feature (unverified) — it is the natural composition of plugin evals' `--ablation` with a per-rule diff. [C]

## Part 3 — Synthesis: the design of an "AI coach per repository"

The precedents split into three families: (1) *private notebooks* written by the agent (Claude auto memory, Windsurf) — cheap, unreviewed, local, never measured; (2) *proposed-then-approved memories* (Cursor, Augment, Devin, Copilot with citations/expiry) — the human is the filter, still no measurement; (3) *static readiness scores* (Factory, agentready) — measurable but blind to what actually happens in sessions. Only Claude Code's plugin/skill evals close the loop with a with/without measurement, and only for components you package. The empirical papers add the sobering fact that instruction files mostly buy efficiency, not correctness, and that generated ones can hurt, so every coach proposal must be treated as a hypothesis to test, not a fact to store. [C]

**Design (each element traces to a precedent above):**

1. **Signals** — collected from what DCC already sees per WorkItem event log plus Claude Code telemetry, never from a one-time scan:
   - *Corrections*: user messages that contradict the previous agent action (Claude `feedback` memories; Augment/Cursor triggers). Detect repeats of the same correction across sessions.
   - *Rejections*: `code_edit_tool.decision=reject`, `tool_decision=reject` with `source=user_*` (OTel).
   - *Outcome*: PR merged without human rewrite (autonomy rate), review rounds, reverted lines within 30 days, CI failures after agent commits, cost and tokens per task (OTel `cost.usage` by `skill.name`/`agent.name`).
   - *Stack facts*: manifests read, CLI commands run, hosts contacted, files read (exactly the `relevance.signals` vocabulary — `manifestDeps`, `cli`, `hosts`, `filesRead`, `cwd`).
   - *Instruction-file health*: CLAUDE.md length vs the 200-line guidance; lines that `/doctor` would call derivable; rules never referenced in any session.
2. **Thresholds** — nothing fires on one event: e.g. same correction ≥2 sessions (Cursor's "repeated corrections"); a stack signal seen in ≥3 sessions or in the manifest; a metric worse than the repo's own trailing baseline, not an absolute. Claude Code's own suggestion caps (once per three sessions, two notifications max) are a good default for nagging frequency.
3. **Proposal** — one of four typed artefacts, each with the evidence attached (Copilot-style citations to the sessions/lines that justify it): (a) a CLAUDE.md / `.claude/rules/*.md` line, (b) a skill, (c) a hook (for rules that must always hold — Anthropic: "convert it to a hook"), (d) a marketplace component (plugin/MCP) with the *minimal toolset flag* pre-filled. Deletions are proposals too (a rule nobody's session ever needed; a component whose tools were never called).
4. **Approval** — a named person approves in DCC (Identity decision), edits or dismisses (Devin/Augment UX); nothing is written to the repo silently ("No silent actions"). Auto memory stays private to the machine; only approved items are promoted to the repo, as Claude's docs already distinguish (`/memory` vs "add this to CLAUDE.md").
5. **Measurement** — every approved change carries an eval: for skills/plugins, `claude plugin eval` with `--ablation with-without` on 3–5 repo-specific prompts, mocks for MCP servers, `--max-cost-usd`; for CLAUDE.md lines, the same harness with the line present/absent; for components, the outcome metrics after adoption vs the trailing baseline. Record Δ, cost, tokens in the WorkItem event log so the proposal's evidence and its result live on one timeline (Event-log decision).
6. **Pruning** — scheduled, not ad hoc: expire unused items (Copilot 28-day rule), re-run the eval suite on every new model release (plugin-evals guidance), propose deletion when Δ≤0 or the item was never used, and keep CLAUDE.md under the 200-line line by moving detail to on-demand skills/rules with globs. The papers justify being aggressive here: cost goes up with every line, correctness usually does not.
7. **Marketplace search fits at step 3d** — search by *diagnosed stack* (manifest + CLI + hosts), query the official Claude marketplace JSON first (314 entries, sha-pinned, vendor-authored), then the official MCP registry by vendor namespace (never by bare keyword), then Docker's catalog for the tool list; filter by trust (vendor namespace, pinned sha, read-only mode available, secrets required), estimate the context cost from the tool count (≈0.5–1K tokens per tool by Anthropic's numbers) and require tool search or a toolset flag above ~10 tools; trial on the repo through the eval harness with mocked servers; keep only if Δ>0 and cost is acceptable; re-check the tool descriptions on update (rug-pull defence). For clients' repositories DCC can ship its own marketplace with `relevance` blocks so Claude Code itself keeps suggesting the right component after onboarding, with the user always confirming.
