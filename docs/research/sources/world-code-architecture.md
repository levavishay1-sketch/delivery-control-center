## 1. Rewrite vs. incremental — the classic evidence and what AI agents change

### 1.3 What the evidence says about when a rewrite pays off *now*

1. Every documented AI-era success is a **mechanical transformation with an oracle**: a language or framework port, an API/library migration, a test-framework migration — where "correct" means "behaves identically" and a compiler, test suite or equivalence check can say so. None of the reports is a "redesign the architecture while rewriting" project.
2. What became cheap is *producing* code (Bun: ~1,300 lines/minute at peak). What did not become cheap is *verifying* it and *deciding* what it should do (Anthropic's "hard part"; METR's slowdown on judgment-heavy work in familiar code).
3. Therefore, in 2026, a rewrite pays off when (a) a behavioural oracle exists or can be built first, (b) the scope is frozen at parity (no second-system feature creep), (c) the old system keeps running and the new one is swapped in piece by piece, and (d) the human budget goes into the rulebook, the tests and the review — not the typing. It does not pay off when the motivation is "it's a mess", "not modular", or "another language would be nicer" without an oracle; the cost then is a multi-week re-discovery of the corner cases the old code already handles, with 1.7× the defect rate of human code (§9) landing all at once.
4. The Microsoft caveat cuts both ways for a 35k-line system: a wholesale replacement is *feasible* at this size, so the strangler façade is optional; but feasibility is not a reason. The decision should be made per module against an oracle, not for the whole system.

### 2.2 Package by feature vs. by layer; hexagonal

- Simon Brown, *Modular monolith / package by component* — https://simonbrown.je/modular-monolith/ (summary) [C, influential]: layered packaging leaks — every "layer" folder grows without bound and nothing stops a controller reaching a repository. Package by component/feature with language-level encapsulation, and "if you can't build a modular monolith, what makes you think microservices is the answer?"
- Vertical slices inside a modular monolith — https://milanjovanovic.tech/blog/where-vertical-slices-fit-inside-the-modular-monolith-architecture and https://www.nilus.be/blog/layered_architecture_vs_vertical_slice_in_modular_monoliths/ (summaries) [C]: the module boundary answers the macro question; slices organise code by use case inside a module; layers only where a module genuinely needs them. Java/Spring community trend (2025) favours package-by-feature for medium/large apps (summary) [C].
- Hexagonal / ports-and-adapters in Node — https://github.com/jbreckmckye/node-typescript-architecture, https://blog.alexrusin.com/future-proof-your-code-a-guide-to-ports-adapters-hexagonal-architecture/ (summaries) [C]: ports are TS interfaces; adapters wrap I/O. Practitioners' caution: "powerful, but not always necessary"; the pay-off is at the boundaries with many external systems. For DCC the real boundaries are exactly four — Claude (CLI/SDK), git, Azure DevOps REST, the database — which is where interfaces earn their keep; applying the pattern to every module is the over-abstraction the same sources warn about.

### 2.3 When to split into services — evidence against premature microservices

- Fowler, *MonolithFirst* / *Microservice Premium* — https://martinfowler.com/bliki/MonolithFirst.html (summary) [C, widely cited]: the microservice premium is a productivity cost that only pays off in sufficiently complex systems; start with a monolith and extract when boundaries are proven.
- Amazon Prime Video (2023) — https://www.thestack.technology/amazon-prime-video-microservices-monolith/ and https://www.devclass.com/ci-cd/2023/05/05/reduce-costs-by-90-by-moving-from-microservices-to-monolith-amazon-internal-case-study-raises-eyebrows/1621790 (summaries) [C]: one video-quality service moved from Step Functions + S3 hand-offs to a single ECS task and cut infrastructure cost by >90% — a caution about distributing before the need is proven, not a general verdict.
- Microsoft CQRS pattern doc (fetched via GitHub source) [A]: not suitable "when the domain or the business rules are simple" or "a simple CRUD-style user interface and data access operations are sufficient".
- **Applied to DCC:** one API process, one MCP process and one web bundle is already the right shape for a solo-maintained product with one pilot client. There is no evidence that splitting further would help; the evidence points to making the *module* boundaries inside `packages/core` explicit and enforced.

## 3. Event sourcing / append-only log + read models

### 3.1 Recognised pitfalls (official pattern docs)

- Microsoft, *Event Sourcing pattern* — https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing (fetched via GitHub source) [A]: eventual consistency between store and projections; **schema evolution** ("events are immutable, so design changes require tolerant deserialization, event versioning, upcasting, or in-place migration — never direct event modification"); replay cost (snapshots add storage and complexity); no standard query mechanism — projections are mandatory; handlers must be idempotent. **When not to use:** "straightforward CRUD operations that don't require auditability"; "prototypes, minimum viable products"; when real-time consistency is required; "domains in which data is mostly static"; "teams don't have experience in event-driven architectures". "Use selectively rather than system-wide."
- Marten docs (JasperFx) — versioning https://martendb.io/events/versioning.html and projection rebuilds https://martendb.io/events/projections/rebuilding.html (fetched via GitHub source) [A]: prefer additive changes (nullable properties, defaults); upcasters transform old JSON on read; "avoid frequent schema versions; model carefully before implementing changes"; rebuilds are clear-then-insert, capped in concurrency, with blue/green projection versions so side effects are not replayed.
- Greg Young, *Versioning in an Event Sourced System* (book) — https://www.goodreads.com/book/show/34327067-versioning-in-an-event-sourced-system [C, classic]; Oskar Dudycz, *How to (not) do the events versioning* — https://event-driven.io/en/how_to_do_event_versioning/ (summary) [C]: strategies = extend non-breakingly, new event type, upcasting, dual publish; "the best option is to prevent conditions in which versioning is needed"; "a new version must be convertible from the old; if not, it is a new event".
- Dudycz's anti-pattern list — https://github.com/oskardudycz/EventSourcing.NetCore (fetched) [B/C]: property sourcing, state obsession, "CRUD sourcing"; linked articles *When not to use Event Sourcing?*, *Stop overselling Event Sourcing as the silver bullet*, *Don't let the Internet dupe you, Event Sourcing is hard*.

### 3.2 Event log vs. audit log vs. hybrid

- Kurrent, *Event Sourcing vs Audit Log* — https://www.kurrent.io/blog/event-sourcing-audit (summary) [C, vendor]; dev.to *Event Sourcing gives you an event store, not an audit log* — https://dev.to/gentlyding/event-sourcing-gives-you-an-event-store-not-an-audit-log-42k (summary) [C]; Dudycz, *Is the audit log a proper architecture driver for Event Sourcing?* — https://event-driven.io/en/audit_log_event_sourcing/ (summary) [C]. Common position: event sourcing's job is to *rebuild state by replay* and drive projections; an audit log's job is to let a third party prove what happened and that it was not rewritten (tamper evidence, retention, read logging). Audit alone does not justify event sourcing: "you could just store events with state change and use them for audit needs and integrations using the outbox pattern". A **hybrid** (events + current-state storage) keeps the audit trail and integration benefits while keeping reads and conflict handling simple.

### 3.3 Where DCC sits and what the guidance is

DCC's foundation (§project.md) is an append-only `event_log` per work item written only through `appendEvent()`, *alongside* mutable current-state tables. State is not derived by replaying events; the log is the record and the integration/timeline source. That is the **hybrid "audit/event log + current-state tables"** pattern — the one the sources above recommend for a small team — not true event sourcing and not CQRS.

Guidance that follows: (1) write the event and the state change in **one transaction** (or an outbox) so the two never diverge — this is the hybrid's one real pitfall; (2) version events additively (`type` + `version`, upcast on read) and keep a test that reads the oldest fixtures; (3) do not advertise or depend on "rebuild by replay" unless a `prove:` script actually does it; (4) do not add projections/eventual consistency until a query or scaling need forces it (Microsoft: use selectively); (5) keep the log's audit properties explicit — append-only triggers (`db:guards`), retention, who/when on every row.

## 4. Multi-tenant Postgres with RLS

### 4.1 Correctness pitfalls (official docs)

PostgreSQL docs (fetched via the SGML sources on GitHub; canonical URLs https://www.postgresql.org/docs/current/ddl-rowsecurity.html, https://www.postgresql.org/docs/current/sql-createpolicy.html, https://www.postgresql.org/docs/current/sql-altertable.html, https://www.postgresql.org/docs/current/sql-set.html) [A]:
- RLS enabled with **no policy → default-deny**; policies on a table with RLS disabled are ignored.
- **Table owners bypass RLS** unless `FORCE ROW LEVEL SECURITY`; superusers and roles with `BYPASSRLS` always bypass. Tests and apps running as the owner "pass" for the wrong reason.
- Permissive policies OR together; restrictive policies AND; at least one permissive policy is needed before restrictive ones matter.
- "Functions and operators marked LEAKPROOF may be evaluated before policy expressions"; non-leakproof user-defined functions in policies or WHERE clauses can leak protected rows through error messages — RLS is defence in depth, not a substitute for careful design.
- Policies are **not applied during referential-integrity checks or constraint validation**, so existence of a row in another tenant can be inferred through FK/unique violations.
- `SET LOCAL` lasts "only till the end of the current transaction, whether committed or not"; outside a transaction it "emits a warning and otherwise has no effect".

### 4.2 Connection pooling and the planner (practitioner consensus + vendor docs)

- Pooling: plain `SET app.tenant …` persists on the pooled connection, so the next request inherits the previous tenant — "the single most common way teams accidentally break tenant isolation"; the only correct pattern under transaction-mode pooling (PgBouncer) is `BEGIN; SET LOCAL app.current_tenant = …; …; COMMIT`. Sources: https://www.bytebase.com/blog/postgres-row-level-security-footguns/, https://queryplane.com/blog/postgres-row-level-security-in-practice/, https://rivestack.io/blog/postgresql-row-level-security, https://imfeld.dev/notes/postgresql_row_level_security (summaries) [C, consistent across sources].
- Planner/performance: Supabase RLS guide — https://supabase.com/docs/guides/database/postgres/row-level-security (fetched via GitHub source) [A]: "add an index on every column your policies filter on"; wrap function calls as `(select auth.uid())` so Postgres runs an initPlan once per statement instead of per row; restrict policies `TO` specific roles. Practitioners add: run `EXPLAIN (ANALYZE, BUFFERS)` at production row counts and look for Seq Scans; a policy that reduces to `tenant_id = $1` uses the index like a hand-written WHERE (summaries) [C].
- AWS, *Multi-tenant data isolation with PostgreSQL RLS* — https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/ (blocked; well-known reference for the `current_setting('app.current_tenant')` + non-BYPASSRLS app-role pattern) [A, not re-read this session].

### 4.3 Drizzle ORM RLS status (2026)

- Support since **0.36.0** (Nov 2024) — https://github.com/drizzle-team/drizzle-orm/releases/tag/0.36.0 (fetched) and https://orm.drizzle.team/docs/rls (summary) [A]: `pgPolicy` (for/to/using/withCheck), `pgRole`, `.enableRLS()`, `.link()` for tables Drizzle does not own, drizzle-kit generates policies and roles (`entities.roles`, with Neon/Supabase exclusions), Neon `crudPolicy`/`authUid`, Supabase `authenticatedRole`/`anonRole`/`serviceRole`, RLS on views via `securityInvoker`.
- Gaps visible in the tracker (fetched) [A, primary]: **#5819 (May 2026) asks for `.forceRLS()`** — i.e. `FORCE ROW LEVEL SECURITY` still cannot be declared in the schema and must be raw SQL in a migration (DCC's `db:guards` territory); #4763 (Jul 2025) asks to disable RLS management in drizzle-kit; there is no built-in per-request tenant-context helper — the pattern is `db.transaction(tx => tx.execute(sql\`SET LOCAL …\`))`. Neon's guide (https://neon.com/docs/guides/rls-drizzle, fetched via GitHub source) [A] adds: run policy migrations over a **direct, non-pooled** connection.

### 4.4 Alternatives

- Shared schema + RLS is the 2025–26 default for B2B SaaS (one migration for all, cheap tenants, simple analytics) with the known cost that isolation depends on discipline — hence defence in depth (app scoping + RLS) — https://www.adiagr.com/blog/07-saas-postgres-multitenancy-patterns/, https://singhajit.com/multi-tenant-database-isolation/ (summaries) [C].
- Schema-per-tenant: easy per-tenant customisation, but migrations × N, pooling and catalog bloat at scale (summaries) [C].
- Citus — https://docs.citusdata.com/en/stable/use_cases/multi_tenant.html (fetched via GitHub source) [A]: `tenant_id` on every table as the distribution key with colocation; needed only when a single node is not enough. Citus 12 adds schema-based sharding.
- Consensus recommendation (summaries) [C]: RLS on shared tables with composite `(tenant_id, …)` indexes, PgBouncer in transaction mode, one `app.tenant_id` convention, and the option to peel off a heavy tenant later.

### 4.5 Testing RLS — how others prove the tenant wall

- pgTAP suites run **as a non-owner, non-BYPASSRLS role**, `SET LOCAL` the tenant, and assert: cross-tenant SELECT/UPDATE/DELETE affect 0 rows; INSERT with a foreign `tenant_id` raises 42501; `SET ROLE` escalation fails; a **generative check** enumerates all tables and fails if any lacks an isolation policy; a **mutation test** removes one policy and confirms the suite fails, then passes when restored. Example with 34 assertions: https://github.com/alexjose/family-tree/pull/22 (fetched) [C]. The five-query recipe: https://dev.to/veristria/the-tenant-isolation-test-five-queries-that-prove-your-boundaries-4gfg (summary) [C]. Why suites pass for the wrong reason (owner/superuser, policy not enabled, permissive OR): https://dev.to/dev_encyclopedia/your-rls-policy-passed-its-test-for-the-wrong-reason-2oah (summary) [C]. Generator: rlsautotest — https://unitautogen.com/postgresql.html (summary) [C]. pgTAP + Supabase walkthrough: https://blair-devmode.medium.com/testing-row-level-security-rls-policies-in-postgresql-with-pgtap-a-supabase-example-b435c1852602 (summary) [C].
- Applied to DCC's `dev:prove` (9 checks incl. the RLS wall): the checklist above is the bar — runs as `dcc_app`, covers all four commands, has the "every tenant table has a policy" generative check, and a mutation test.

## 5. PGlite as the embedded dev database

### 5.1 Official limits

- "PGlite is single user/connection" — Postgres single-user mode because WebAssembly cannot fork; intended uses: "unit and CI testing", "local development", edge/RAG — https://github.com/electric-sql/pglite and https://pglite.dev/docs/about (fetched README/docs source) [A].
- Multi-tab in the browser is handled by a worker with **leader election**; there is no equivalent for several Node processes on one data directory (fetched docs) [A].
- **pglite-socket** — https://github.com/electric-sql/pglite/blob/main/packages/pglite-socket/README.md (fetched) [A]: one process owns the data directory and serves the Postgres wire protocol to other processes/psql; a multiplexer over the single connection, "not all use cases are guaranteed to work".
- v0.4 (Mar 2026) is a new architecture with separate `initdb` and connection multiplexing (multiple *logical* connections in one process); v0.5 moves to Postgres 18.3 and splits extensions into packages — https://github.com/electric-sql/pglite/blob/main/packages/pglite/CHANGELOG.md (fetched), https://electric.ax/blog/2026/03/25/announcing-pglite-v04 (summary) [A].

### 5.2 Practitioner failure reports (the "one process at a time" rule is real)

- Two Node processes open one data dir → **silent fork**: each sees only its own writes, no error, last closer wins; trigger: `pnpm build` while `pnpm dev` runs; fix: PID lock file, refuse a second opener, treat stale locks by liveness — https://github.com/AaronBuxbaum/diveday/issues/1325 (fetched) [C].
- Lock stolen after 5 minutes without heartbeat → **WAL corruption**, full re-import — https://github.com/garrytan/gbrain/issues/2058 (fetched) [C].
- Many Node processes initialising PGlite concurrently → intermittent **SIGSEGV** in Node/V8 (Bun/Deno unaffected), issue open — https://github.com/electric-sql/pglite/issues/1053 (fetched) [A, primary tracker].
- **Concurrency tests pass vacuously**: the single connection serialises transactions, so `FOR UPDATE` never blocks; gate such tests to real Postgres — https://github.com/leomontigatti/en-escena/issues/1045 (fetched) [C].
- Request for concurrent databases in Node for parallel tests — https://github.com/electric-sql/pglite/issues/324 (fetched) [A].

### 5.3 How others use it, and the alternatives

- Vitest + Drizzle + PGlite with a fresh in-memory DB per test and snapshots: ~1.3 s suite vs ~4.8 s with Testcontainers; caveat "subtle differences or unsupported features vs native Postgres" — https://nikolamilovic.com/posts/fun-sane-node-tdd-postgres-pglite-drizzle-vitest/, https://makerkit.dev/blog/tutorials/unit-testing-prisma-vitest (summaries) [C].
- Testcontainers (Node, PostgreSQL module) — https://node.testcontainers.org/modules/postgresql/ (fetched via GitHub source) [A]: real image, needs Docker, snapshot support; seconds of start-up.
- Neon branches — https://neon.com/docs/introduction/branching (summary) [A vendor docs]: copy-on-write branch per developer / PR / CI run, auto-expiry; production-shaped data without copies.
- **Guidance for DCC:** keep PGlite for unit tests and the zero-install dev DB, but (a) add a PID lock so a second opener is refused instead of silently forking, or run PGlite behind pglite-socket in the API process and point one-off scripts at it; (b) run anything that needs concurrency, roles, `FORCE RLS` or migration fidelity — the `dev:prove`/`smoke` family — against real Postgres in CI (Docker/Testcontainers or a Neon branch).

## 6. Language choice for this workload

- **Anthropic Agent SDK is Python and TypeScript only.** "To drive the same agent loop from a language other than Python or TypeScript, run the CLI as a subprocess with the `-p` flag and `--output-format json`" — https://code.claude.com/docs/en/agent-sdk/overview (fetched) [A]. The **official C# SDK** (`Anthropic` NuGet v10+, .NET Standard 2.0, `IChatClient`, MCP C# SDK) covers the Messages API, not the Claude Code harness — https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/csharp (fetched) [A]. **Managed Agents** (beta, `managed-agents-2026-04-01`, REST + SDKs + `ant` CLI, managed or self-hosted sandboxes) is the language-agnostic hosted harness — https://platform.claude.com/docs/en/managed-agents/overview (fetched) [A]. Implication: a .NET/Go/Rust core would talk to Claude Code through a subprocess or through Managed Agents, losing in-process `canUseTool`, hooks, session stores and typed messages (§7).
- **Throughput.** TechEmpower Round 23-style comparisons put .NET/Go 2–5× ahead of Node on synthetic plaintext/JSON, narrowing to ~1.9× on I/O-realistic tests and "one .NET server replaces two Node servers" on DB-bound work — https://dev.to/insight105/on-web-framework-performance-a-net-10-reality-check-4ep5, https://dev.to/tuananhpham/popular-backend-frameworks-performance-benchmark-1bkh (summaries) [B]; a fair laptop benchmark with connection pooling: Go fasthttp 8,054 rps vs Node cluster 3,950 rps, author: "the difference may not be that dramatic" when configured properly — https://github.com/nDmitry/web-benchmarks (fetched) [B]. DCC's load is a handful of concurrent Claude sessions, ADO REST calls and git; latency is dominated by the model and the network, not the runtime. There is no benchmark evidence that the runtime is DCC's bottleneck.
- **Polyglot cost.** Each extra language adds a compiler/package manager/CI pipeline, hiring and onboarding surface and knowledge silos; single-language full-stack teams claim 20–40% productivity gains (unsourced); "start with one language until there is a clear performance, productivity or domain reason" — https://vercel.com/i/monorepos-full-stack-teams, https://ertyurk.com/posts/polyglot-monorepos-when-your-backend-and-frontend-speak-different-languages/, https://nowah.xyz/blog/typescript-end-to-end-one-language (summaries) [C]. The React UI stays TypeScript in every scenario, so any backend language change makes the repo polyglot by definition.
- **The .NET argument.** Real: the software house's clients are .NET/Dynamics shops, so client staff could operate/extend a .NET backend, Microsoft Agent Framework 1.0 (Apr 2026, .NET + Python) exists, and the official C# SDK exists. Against: DCC's distinguishing capability is orchestrating *Claude Code* (hooks, skills, `.claude/` conventions, session resume, cost fields) — all TS/Python-first; docx parsing is available in both ecosystems (mammoth vs Open XML SDK) so it does not decide anything; a port is exactly the oracle-less rewrite §1 warns against. If a client needs on-prem .NET operation, the evidence-backed route is a thin .NET (or any-language) integration over DCC's HTTP API or Managed Agents, not a port of the core.
- **Verdict:** no evidence of a material advantage from Go, Rust, .NET or Python for this I/O-bound orchestrator; the strongest single fact is the SDK's language support.

## 7. Orchestrating Claude Code from a product (September 2026)

All from Anthropic's docs unless noted (fetched) [A]. Versions seen: Claude Code 2.1.283; TypeScript Agent SDK 0.3.283; Python Agent SDK 0.2.160 (not at full parity with TS).

- **What Anthropic recommends.** Agent SDK when "software is at the keyboard" (a product feature, a pipeline, a bot); the CLI for interactive terminal use; the Client SDK for raw API; Managed Agents when Anthropic should host the loop — https://code.claude.com/docs/en/agent-sdk/overview. Third-party products may not offer claude.ai login/rate limits (use API keys), and may not be branded "Claude Code".
- **Headless CLI (`claude -p`)** — https://code.claude.com/docs/en/headless: `--output-format json|stream-json`, `--json-schema` for validated structured output (`structured_output` field), `--resume <session-id>` / `--continue` (session found from any directory since v2.1.223; a `.jsonl` path also works), `--allowedTools`, `--permission-mode auto|dontAsk|acceptEdits`, `--permission-prompts none` for unattended runs, `--bare` ("the recommended mode for scripted and SDK calls, and will become the default for `-p`") which skips hooks, skills, commands, subagents, plugins, MCP, memory and CLAUDE.md unless passed explicitly; `SIGTERM` → exit 143 with SessionEnd hooks run; `system/init` event with plugin/MCP load errors for CI gating; `permission_denials` in the result.
- **Security of `-p` in a cloned client repo** — https://code.claude.com/docs/en/permissions ("What runs before you trust a folder"): without `--bare`, a `-p` session runs the project's `.claude/settings.json` hooks and connects `.mcp.json` servers with no trust dialog. DCC clones third-party repositories; this is a concrete reason to run onboarding with `--bare` plus explicit `--settings`/`--mcp-config`.
- **Interactive needs without a terminal** — https://code.claude.com/docs/en/agent-sdk/user-input and https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode: the SDK's `canUseTool` callback receives permission requests *and* `AskUserQuestion` (1–4 questions, 2–4 options, optional HTML/markdown previews) so the product renders them in its own UI; `PreToolUse` hook `defer` lets the process exit and resume later; **streaming input mode is "the preferred way"** for interactive products (queued messages, interrupts, images, persistent session). A PTY is therefore not needed for interactivity.
- **`/init` is the exception.** The commands reference — https://code.claude.com/docs/en/commands — marks `/init` (incl. `CLAUDE_CODE_NEW_INIT=1`'s interactive flow through skills, hooks and memory) as **interactive only: not available in `-p` or the SDK**, together with `/desktop`, `/design`, `/permissions`, `/install-github-app`, `/install-slack-app`. Issue #837 (https://github.com/anthropics/claude-code/issues/837, fetched) confirms custom commands/skills work in `-p` while built-in interactive commands do not. So DCC's PTY-driven `/init` is the only way to get that flow today, and it inherits the TUI's fragility: concurrent sessions in one directory tear `settings.json` (#91520), `exclusiveCwd` regressions (#91745), refresh-token races (#91009), PTY lifecycle bugs (#93151) — https://github.com/anthropics/claude-code/issues (fetched search). Alternative worth testing: generate the same artefacts with `claude -p "/init-like skill"` plus `--append-system-prompt`, keeping the PTY only if the interactive flow's questions are the product feature.
- **Hooks** — https://code.claude.com/docs/en/hooks and https://code.claude.com/docs/en/agent-sdk/hooks: fire identically in terminal, SDK and headless; `SessionEnd` cannot block; settings are snapshotted at session start; the SDK adds in-process callback hooks and still runs settings.json hooks when `settingSources` is enabled (default).
- **Sessions** — https://code.claude.com/docs/en/agent-sdk/sessions and https://code.claude.com/docs/en/agent-sdk/session-storage: transcripts in `~/.claude/projects/<encoded-cwd>/*.jsonl`; `resume`, `continue`, `fork`; `SessionStore` adapters (S3/Redis/Postgres examples) mirror transcripts for multi-host resume; Anthropic's own advice: "Don't rely on session resume … capture the results you need as application state and pass them into a fresh session's prompt. This is often more robust than shipping transcript files around."
- **Cost reporting** — https://code.claude.com/docs/en/agent-sdk/cost-tracking: `total_cost_usd` and `modelUsage` are **client-side estimates** from a bundled price table ("Do not bill end users or trigger financial decisions from these fields"); use the Usage & Cost API for billing; `usage` excludes subagents, `modelUsage` includes them; resumed sessions report whole-session totals since v2.1.277; per-step `output_tokens` is a placeholder.
- **Structured output** — https://code.claude.com/docs/en/agent-sdk/structured-outputs: JSON Schema draft-07 (Zod with `target: "draft-7"`), re-prompt on mismatch, `error_max_structured_output_retries`.
- **Quality workflow built in** — https://code.claude.com/docs/en/code-review: `/code-review` (formerly `/simplify`; `/simplify` now a cleanup-only pass) runs reviewers for correctness plus reuse/simplification/efficiency, `--fix` applies them, runs in the foreground under `-p`; hosted Code Review costs ~$15–25 per PR.

## 9. AI-generated codebases — what the 2025–2026 studies show and how people remediate

### 9.1 Studies

- **GitClear, *AI Copilot Code Quality* (2025)** — https://www.gitclear.com/ai_assistant_code_quality_2025_research (summary) [B]: 211M changed lines; churn (code reverted/rewritten within two weeks) from a pre-AI 3.3% to 7.1% in 2025; duplicated blocks up **8×** in 2024; copy/pasted lines exceeded moved (refactored) lines within commits for the first time.
- **GitClear, *The Maintainability Gap* (2026)** — https://www.gitclear.com/the_ai_code_quality_maintainability_gap (summary) [B]: 623M changes 2023–26; cross-file function calls (reuse) **−35%**, refactoring moves **−70%**, long-term legacy maintenance **−74%** vs 2022; error masking **+47%**; commits containing a duplicated block ~10× over two years. Conclusion: "today's default AI workflow is incentivized to deliver atomic code while quietly taxing reuse, consolidation, and error-surfacing."
- **CodeRabbit, *State of AI vs Human Code Generation* (Dec 2025)** — https://www.coderabbit.ai/newsroom/state-of-ai-vs-human-code-generation-report (summary) [B]: 470 open-source PRs; AI-assisted PRs averaged **10.83 issues vs 6.45** (≈1.7×); logic/correctness 1.75×, maintainability 1.64×, security 1.57×, performance 1.42×; XSS 2.74×, insecure deserialization 1.82×; 1.4× more critical and 1.7× more major issues.
- **METR RCT** (§1) [A]: −19% on experienced developers in familiar mature repos, with a +20% perceived gain.
- **Veracode, *2025 GenAI Code Security Report*** — https://www.veracode.com/resources/analyst-reports/2025-genai-code-security-report/ (**not fetched; from memory, not verified this session**) [B]: ~45% of AI-generated samples across 100+ models contained OWASP-class flaws; XSS and log-injection tasks failed most often; newer models were not materially safer.
- Academic reviews (arXiv, blocked — titles only): *Vibe Coding: Practice, Performance, Productivity, and Risk — A State-of-the-Art Review* (2608.20446); *Benchmarking the Quality Gap Between Human-Written and AI-Generated Code* (2609.12708); *Self-Admitted GenAI Usage in Open-Source Software* (2507.10422); *Software Engineering in the Agent Era* (2609.04630) — https://arxiv.org/abs/<id>.
- Vendor/blog statistics ("tech debt +30–41%", "maintenance +300% within 18 months", "vibe-coded projects average 12% test coverage") — e.g. https://vallettasoftware.com/blog/post/vibe-coding-technical-debt, https://keyholesoftware.com/vibe-coding-trends-2026/ (summaries) [C, unsourced]: do not rely on them. The mechanism they describe is plausible and matches GitClear: each prompt's output is locally consistent but globally redundant because the model does not see the whole codebase.

### 9.2 Recommended remediation (what the vendors and practitioners converge on)

- Anthropic's best practices — https://code.claude.com/docs/en/best-practices (fetched) [A]: "Give Claude a way to verify its work" (tests, build, lint, screenshot) and gate the stop on it (`/goal`, a Stop hook as a deterministic gate, a verification subagent); "explore, then plan, then code" but "if you could describe the diff in one sentence, skip the plan"; short CLAUDE.md ("would removing this cause Claude to make mistakes?"); adversarial review in a **fresh subagent** that sees only the diff and the criteria — with the explicit warning that a reviewer told to find gaps will report some and "chasing every finding leads to over-engineering: extra abstraction layers, defensive code, and tests for cases that can't happen"; Writer/Reviewer sessions; fan-out with `claude -p` on a task list after testing the prompt on 2–3 files.
- Built-in cleanup passes: `/code-review --fix` (reuse, simplification, efficiency, correctness) — https://code.claude.com/docs/en/code-review; the `code-simplifier` plugin agent that "preserves exact functionality" while removing redundancy, over-abstraction and nesting and aligning with CLAUDE.md conventions — https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-simplifier/agents/code-simplifier.md (fetched) [A].
- Structural guards so the debt cannot regrow: architecture tests (ts-arch/dependency-cruiser) and duplication/dead-code gates (jscpd/knip) in CI, plus a periodic "consolidation pass" (sweep clones, unify helpers, delete unused exports) scheduled like any other maintenance — the GitClear signals (refactor share, duplication, cross-file reuse) are the metrics to watch monthly.

## Decision rules the evidence supports

1. **Do not rewrite the system to fix "mess".** Every AI-era rewrite success (Google, Airbnb, Anthropic/Bun) had a behavioural oracle — tests, a compiler, an equivalence check — and a frozen "behave identically" scope. "Not modular / not generic / duplicated" is not an oracle. [§1]
2. **Decide per module, not for the system.** At ~35k lines the strangler façade is optional (Microsoft: small systems can be replaced wholesale), so the unit of decision is one module with one oracle: re-implement behind the same interface, prove parity with the same `prove:`/`smoke` checks, delete the old code in the same change. [§1, §2]
3. **Build the oracle first, then let agents type.** Front-load the human budget into the rulebook, the parity tests and the review (Anthropic's own "hard part"); expect no speed-up on judgment-heavy work in code you know well (METR −19%) and large speed-ups on mechanical, oracle-backed transformations. [§1]
4. **Run a two-week spike before any commitment**: take the worst module, write its oracle, let agents re-implement it, measure cost, defects and review time, and extrapolate. Only that number, not a plan, says whether "rebuild" beats "improve". [§1]
5. **Freeze scope at parity for anything rebuilt.** The second-system effect and AI's tendency to over-generate compound; new features come after parity. [§1, §9]
6. **Stay in TypeScript.** The Claude Agent SDK is TS/Python-only; other languages get a subprocess or Managed Agents; there is no benchmark evidence the runtime limits an LLM/REST-bound orchestrator; a polyglot repo is the cost with no measured benefit. Serve .NET clients through DCC's HTTP API, not by porting the core. [§6]
7. **Target a modular monolith, packaged by feature, enforced by tools**: dependency-cruiser in CI, eslint-plugin-boundaries in the editor, TS project references for direction, ts-arch tests in `npm test`; adopt packwerk-style — baseline today's violations, forbid new ones, burn the list down. Ports/adapters only at the four real boundaries (Claude, git, ADO, DB). No service split without a proven need. [§2]
8. **Keep the hybrid log, do not become event-sourced.** Append-only `event_log` + current-state tables is the recommended pattern for a small team; write both in one transaction, version events additively with an upcast-on-read test, add projections/CQRS only when a query need forces it. [§3]
9. **Harden RLS the way the docs demand**: app role without `BYPASSRLS`, `FORCE ROW LEVEL SECURITY` in raw SQL (Drizzle cannot declare it, issue #5819), tenant context only via `BEGIN; SET LOCAL`, an index on every policy column, `(select …)`-wrapped functions, `EXPLAIN ANALYZE` at production counts. [§4]
10. **Prove the tenant wall like the pgTAP suites do**: run as the app role, cover SELECT/UPDATE/DELETE/INSERT, add a generative "every tenant table has a policy" check and a mutation test that deletes a policy and expects failure; run it in CI on real Postgres. [§4]
11. **Treat PGlite as a single-opener dev/test engine**: add a PID lock that refuses a second opener (silent fork and WAL corruption are documented), or serve it through pglite-socket from the API process; run concurrency, roles and migration proofs on Docker/Testcontainers or a Neon branch. [§5]
12. **Move product-side orchestration to the Agent SDK**: `canUseTool` + `AskUserQuestion` rendered in DCC's UI, streaming input mode, `SessionStore` for durability, `--bare` for scripted runs in cloned client repos; keep the PTY only for the interactive `/init` flow, isolated and one-per-directory, and treat cost fields as estimates. [§7]
13. **Gate quality in CI with the industry defaults**: jscpd ≤ 3% (fail on new duplication), complexity ≤ 15 cognitive / 20 cyclomatic, functions ≤ 50–80 lines, zero knip findings, zero cycles, coverage ≥ 75% in `packages/core` on new code. [§8]
14. **Institutionalise the agent-era loop**: verifier (typecheck/lint/tests) → fresh-context adversarial review → `/code-review --fix` or simplifier pass → merge; schedule a monthly consolidation sweep and track duplication, refactor share and cross-file reuse — the signals GitClear shows eroding in AI-heavy repos. [§9]
15. **Keep the old system running throughout.** Whatever is rebuilt ships behind the same API on a task branch, is proven, then replaces the old code in the same change — the pattern behind every successful rewrite in the classic stories and the repo's own "the change is not done until the old one is gone" rule. [§1, §2]
